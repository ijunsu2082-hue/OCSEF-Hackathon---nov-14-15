# Infrastructure development procedures

Operational companion to [Infrastructure lifecycle workflows](./INFRASTRUCTURE-WORKFLOWS.md). This document expands intake, feasibility, land and engagement, and engineering continuity into usable procedures. It defines workflow records and controls, not legal, emergency-response, engineering, procurement, or permitting rules. Configure authority, thresholds, retention, privacy, and external requirements from each owner's current approved sources. Examples and values below are illustrative only.

## How to use this procedure

Each procedure has a stable ID (`DEV-*`) for cross-document references. A case manager opens linked work items, assigns role holders, records evidence versions, and advances gates only after named reviewers accept their inputs. A role is a responsibility; map it to actual people and delegations in the owner directory. Record local source, revision/date, and reviewer whenever a threshold or requirement is configured. Unknown, not applicable, blocked, waived, and pending are distinct states; a waiver needs authority and rationale.

## Shared records and controls

Every case record carries stable case ID, parent/related case IDs, asset/site/route references, lifecycle status, accountable owner, source, created/updated timestamps, sensitivity/access class, current version, and audit trail. Every work item carries ID, procedure ID, deliverable, responsible role/person, accountable reviewer, due date and basis, dependencies, status, blocker/exception, evidence links, and completion acceptance. Never overwrite earlier submissions, assumptions, maps, designs, or decisions; mark superseded and link successor.

Evidence register fields: evidence ID; title/type; author/issuer; source URL or file reference; received/issued date; version; geography/asset scope; related requirement, parcel, option, interface, work item or decision; confidence/limitations; reviewer and review state; expiry/review date; confidentiality; supersedes; checksum if supported. Decisions record question, options, recommendation, decision authority, rationale, dissent, conditions, date, evidence, and revisit trigger/date. These fields support traceability; they do not establish technical validity by themselves.

Handoffs require a named sender and receiver, date/time, package/version, unresolved items, requested action, acknowledgement, and next checkpoint. If receiver does not acknowledge by configured time, alert case owner; do not treat silence as acceptance. Log changes with actor, time, old/new values, reason, impact assessment, approver when required, and affected downstream records.

## DEV-01 — Register need or event

**Purpose and trigger.** Create durable record from service need, observed defect, outage, hazard, customer/community request, planned program, or follow-up to an incident. Emergency reporting path must show owner-configured escalation contacts and any configured notice that the workspace is not an emergency dispatch channel.

**Roles.** Reporter supplies observation; intake coordinator checks completeness and routes; duty lead owns urgent triage; asset owner validates asset link; case manager accepts ongoing lifecycle; privacy/security reviewer handles restricted content. One person may hold several roles only where configured delegation permits.

**Intake form schema.** `report_id` (system ID); received timestamp/time zone; reporter name/contact or anonymous flag; preferred callback channel; source/channel; event/need type; observed facts in reporter's words; observed time and time confidence; location geometry or text, coordinate system/source, positional uncertainty, access restriction; asset ID or “unknown”; affected service/population, extent and duration if known; immediate action already taken and by whom; current service condition; urgency category from owner-configured list; known hazard/safety concern; incident/external reference; attachments and provenance; personal/sensitive data flag and handling note; consent/contact limitation where applicable; duplicate candidates; intake coordinator; next update due; missing fields with owner and due date.

Keep reported observation distinct from verified finding. Avoid collecting unnecessary personal data. Restrict reporter-visible data from internal notes and sensitive locations. Original submission stays immutable; corrections are additive, attributed entries.

**Procedure.** 1) Register submission and preserve source evidence. 2) Screen for immediate danger using the owner's approved triage path; if urgent, hand off to the designated response authority and record acknowledgement, without making the product a substitute for that response. 3) Check duplicates by asset/location/time/description; link candidates, never auto-merge. 4) Resolve or mark asset/location uncertainty. 5) Assign duty lead and next action/date. 6) Request missing information without blocking urgent routing. 7) Accept, defer, link to an existing case, or reject with reason and notifying role. 8) If accepted, assign lifecycle case manager and transfer the intake packet.

**Decision and handoff.** Duty/triage role sets urgency and route under locally configured criteria. Asset owner confirms relationship, not necessarily root cause. Case manager confirms acceptance and ongoing owner. Handoff packet includes report, location uncertainty, current condition, affected service, actions and acknowledgements, privacy label, open questions, and next update commitment.

**Exceptions.** Anonymous report: preserve source and route by available facts. Unknown asset: create unresolved location task; do not invent asset link. Conflicting accounts: retain both and assign verification. Duplicate: link and state which record is canonical, with rationale. Out-of-hours: use configured rota/escalation, log attempted and successful contact. Sensitive information: restrict, redact for broad exports, and assign authorized custodian. Reporter unreachable: record attempts and proceed using available evidence where authorized.

**Acceptance.** Intake accepted only when source retained, decision recorded, urgency/route set, accountable role assigned, next action and date present, and unresolved critical information has owner. Emergency branch additionally needs response handoff acknowledgement or documented failed-contact escalation. Rejected/deferred cases retain reason and review path.

## DEV-02 — Emergency coordination and stabilization record

**Purpose.** Track infrastructure-related response coordination and transition into planned recovery. This record supports accountable handoffs; competent emergency authorities retain operational command under their own procedures.

**Event log schema.** Case/incident IDs; event timestamp/time zone; observed condition and source; affected asset/service/location; impact known/unknown; severity category and basis under configured playbook; current incident commander/response contact role; decision/action; owner; communication channel; recipient and acknowledgement; next update; status; evidence; personal-data classification. Record facts and attributed reports separately from assessment.

**Sequence.** Record incoming alert and callback. Route to configured duty contact; record contact attempt and acknowledgement. Capture only verified immediate status and state unknowns explicitly. Log each transfer with sender/receiver, timestamp, asset/service state, current restrictions, open hazards, actions taken, and next report time. Maintain incident link and evidence references. When immediate response authority declares coordination handoff complete, schedule stabilization review; do not infer resolution from elapsed time or silence.

**Stabilization review.** Asset owner and operations lead assemble timeline, service interruption/restoration state, temporary measures, outstanding hazards, monitoring needs, damage/condition evidence, affected parties, and residual restrictions. Engineering/safety reviewers identify required inspections or controls using owner-approved criteria. Sponsor and asset owner decide whether follow-up becomes a capital/renewal case, maintenance work, monitoring task, or no further action; link records and rationale.

**Emergency-to-capital conversion.** Create linked capital case when durable repair, replacement, resilience improvement, or funded permanent work is needed. Carry forward need statement, incident chronology, verified service baseline, temporary works, damage and inspection records, restrictions, stakeholder commitments, open permits/land constraints, and urgency rationale. Re-run feasibility and option appraisal for permanent solution; emergency choice does not automatically become preferred permanent design. Keep incident and capital records linked but with separate status, authorities, evidence, and closure criteria. Record interim measure owner, inspection/expiry/review date, and exit condition. No capital case may silently close incident obligations.

**Acceptance.** Response coordination branch closes only on named response authority/asset owner acknowledgement, current service condition and residual risks recorded, temporary measures assigned, and next lifecycle disposition approved. Capital conversion requires linked case ID, sponsor, initial scope, funding/authorization path, unresolved baseline gaps, and accountable project owner.

## DEV-03 — Triage and establish service baseline

**Purpose.** Convert accepted intake into a decision-ready description of what service exists, who depends on it, and what outcome needs improvement. Baseline date and evidence boundary must be explicit.

**Baseline schema.** Service name/function; owner and operator (separate fields); service boundary and interfaces; geographic coverage; dependent communities/users/assets; service hours or operating pattern; capacity/demand measure and units; observed/recorded load with period and source; performance/reliability/resilience measures with definitions and period; planned/unplanned outage history and completeness; asset condition/remaining life and inspection date; critical dependencies (power, water, communications, access, upstream/downstream systems, vendors); operating/maintenance staffing and skill assumptions; safety/environmental/community constraints; existing commitments/levels; seasonal/peak variation; data owner and custodian; confidence and known exclusions; baseline as-of date; reviewer and next review trigger.

**Responsibility matrix.** For each service and asset, name accountable owner (sets service outcome and accepts risk), operator (controls daily service), maintainer (performs upkeep), data custodian (defines source and access), design authority (accepts design), incident authority, funding authority, and external interface owner. Record organization/person, scope, delegation/source, contact route, effective dates, and unconfirmed status. Do not infer responsibility from asset location, invoice, or historical practice. Conflicts go to sponsor/asset owner for resolution before a gate that depends on the role.

**Data-gap register schema.** Gap ID; field/claim affected; why needed and decision affected; current evidence and source date; confidence/limitations; missing/contradictory data; owner; method to close (survey, inspection, records request, measurement, interview, model); required access/consent/permit; estimate of effort/cost/duration if known; due date; dependency; interim assumption and its bounds; risk if unresolved; reviewer; closure evidence and acceptance date. Distinguish “not measured,” “not available,” “not applicable,” and “disputed.”

**Procedure.** Hold baseline workshop with owner, operator, maintainer, and data custodian. Confirm service boundary and units before collecting values. Trace each material value to dated source and definition. Compare sources; record discrepancies instead of silently selecting one. Mark value verified, estimated, reported, stale, disputed, or unknown using configured vocabulary. Identify critical gaps and commission appropriate investigation. Assign accepted baseline version and freeze it as appraisal reference; updates create new version and variance note.

**Decision criteria.** Progress when service objective can be stated measurably or decision authority accepts a qualitative objective; accountable owner/operator are identified or explicit resolution action is assigned; major dependencies and material data gaps have owners; baseline date, provenance, and confidence are visible. A low-confidence baseline may support scoped study or provisional options, not false precision.

**Acceptance.** Baseline package includes service map/boundary, responsibility matrix, dated measures and definitions, source register, gap log, reviewer acceptance, and named owner for future updates. A decision using an unresolved gap must cite that gap, sensitivity, and condition/revisit trigger.

## DEV-04 — Define need and appraisal frame

**Roles.** Sponsor owns need and outcome; service owner validates outcome; planner coordinates options; technical leads supply discipline evidence; finance estimates costs; operations assesses operability; community/environmental reviewers assess impacts; decision authority approves appraisal frame.

**Need statement schema.** Need ID; linked intake/incident; service and population; baseline/version; problem or opportunity; desired outcome and measure; performance horizon; geographic scope; constraints; mandatory owner-configured requirements and source; exclusions; dependencies; urgency and consequence of deferral; assumptions; confidence; sponsor; reviewers; approval and date.

Agree appraisal frame before scoring: do-minimum/do-nothing baseline; credible strategic, technical, location, phasing, demand-management, and hybrid options; screening criteria; qualitative/quantitative method; units/base year/currency for costs; analysis horizon and discount assumptions only where owner-configured; risk/uncertainty treatment; impact categories; weights and authority; evidence quality rules; sensitivity cases; decision date. Document each rule's authoritative source and version. Do not imply statutory compliance or engineering adequacy from a score.

**Procedure.** Validate need against baseline; separate symptoms from objectives. Identify no-build, maintenance, demand-side, rehabilitation, replacement, and expansion paths where relevant to case. Screen fatal constraints separately from preferences and label who confirms each. Allow options to be combined or staged. Create appraisal version and obtain frame approval before comparative ranking. If emergency interim response constrains study, state scope and planned permanent reappraisal.

**Acceptance.** Signed-off need and frame; traceable objective; alternatives include baseline and credible candidates or documented why not; criteria, units, weights, source, version, and decision authority recorded. Changes to objective or weights create a new appraisal version and explain ranking impact.

## DEV-05 — Build, compare, and select alternatives

**Option schema.** Option ID/name/status; geometry/site/route; scope and phasing; service outcome; capacity/load assumptions; reliability/resilience approach; constructability/access; land/control path; external approvals/conditions; interfaces/dependencies; capital and lifecycle cost range with estimate class/basis/date; schedule range and critical path; operating model, staffing, maintenance, energy/consumables; environmental/community/health impacts and distribution; safety/security/cyber considerations; deliverability and procurement route; risks/opportunities; data gaps; evidence links; assumptions; confidence; author/reviewer; version.

For each criterion, store measure, unit, direction, source, value or qualitative rationale, uncertainty, assessor, and confidence. Keep raw evidence separate from normalized score. Show unknown and not-applicable values distinctly. Record exclusions and screening reason, including affected decision authority. Use ranges/scenarios when evidence supports ranges; never fabricate decimal precision. Show whole-life cost and affordability separately from funding availability. Log dissent and trade-offs.

**Procedure.** Develop options to comparable scope and maturity. Conduct discipline and operations review. Screen against owner-configured mandatory constraints; refer unresolved legal/permit/land/technical questions to qualified reviewers. Evaluate against approved frame. Run sensitivity on material assumptions/weights and identify rank reversals. Record no viable option or no-go where appropriate. Decision authority selects, rejects, or requests study with rationale, conditions, unresolved risk owners, and revisit triggers. Preserve candidate and rejected versions.

**Decision record.** Decision ID; appraisal version; options considered; recommendation; selected option or no-go; rationale and trade-offs; criteria/weight version; affordability/funding caveats; dissent; conditions; required studies; authority/delegation; participants; date; approval evidence; review date/trigger.

**Exceptions.** No viable option: document constraints and next action, do not force a preferred choice. Incomplete data: label provisional decision, confidence, guardrails, and study owner. Route/site unavailable: reopen affected options and identify changed assumptions. Demand shift: issue new baseline/appraisal version and quantify impact. Emergency interim option: separately identify temporary duration, owner, exit criteria, and permanent decision gate.

**Acceptance.** M1 package has approved need/frame, baseline link, comparable option records, source-linked appraisal, sensitivity, material risks/gaps, and authorized decision. Provisional selection must expose conditions and block downstream commitments that depend on unresolved conditions unless authority explicitly releases them.

## DEV-06 — Maintain dependency and decision readiness

Create milestone/dependency register with item ID, predecessor/successor, responsible owner, required input/version, need-by date, lead-time basis/source, slack or uncertainty, status, blocker, escalation date, and affected gate. Distinguish hard prerequisite from coordination preference. Map land access, surveys, utility data, permits, community commitments, finance, design inputs, procurement, and operations readiness. A dependency owner acknowledges assignment and reports forecast with evidence.

At weekly or configured review, case manager checks critical-path changes, overdue data gaps, expiring evidence, unresolved authority, and decisions due. Escalation reports impact and decision needed, not only lateness. Reforecast changes retain prior forecast, reason, source, approver, and downstream milestones affected. Acceptance: no gate displays “ready” while an unaccepted prerequisite is hidden; authorized conditional release lists scope limits, owner, due date, and stop condition.

## DEV-07 — Screen site, parcel, and route

**Roles.** Sponsor defines footprint; land lead owns records and contacts; surveyor/engineer defines spatial needs; asset owner confirms interfaces; community liaison handles public engagement; counsel and authorized signatory review instruments; environmental/heritage/access specialists review assigned constraints.

**Site register schema.** Site/route ID and option ID; geometry, coordinate reference, source/date/accuracy; parcel IDs and boundary source; recorded owner and verification status/as-of; occupant/tenant/other interest if lawfully collected; contact preference and authority; site access limits; proposed footprint/area/route and temporary workspace; existing easements/rights/utility corridors and source; land-use/physical constraints; environmental/heritage/community sensitivity with access class; survey/title/condition diligence status; third-party interfaces; acquisition/lease/license/easement/access instrument path (configurable); valuation basis/date/status where applicable; negotiation owner; confidentiality; risks; next action/date.

**Procedure.** Define functional footprint and alternatives before parcel-level engagement where feasible. Verify spatial reference, parcel data provenance, ownership status, and limits of mapping. Record uncertainty and order survey/title/utility/environmental diligence as needed. Screen site access, construction laydown, permanent operation, maintenance access, outages, and restoration. A route change triggers impact review of affected parcels, consultation, diligence, design interfaces, and approvals. Restrict sensitive property terms and vulnerable locations by role.

**Acceptance.** Each candidate has mapped geometry/provenance, affected parcel list or explicit unknown, ownership verification status, access/diligence plan, constraint log, and named decision owner. Map display is not proof of title, boundary, right, or permission.

## DEV-08 — Engage landholders and negotiate control path

**Engagement log schema.** Interaction ID; parcel/site; person/organization and verified role; contact authority/source; preferred channel/language/access needs; purpose; date/time; attendees; materials/version provided; factual summary; questions/concerns and attribution; commitments made by each party; follow-up owner/date; confidentiality; consent/notice status as configured; next step; evidence/recording reference; reviewer. Keep community outreach record separate from confidential property negotiation; link only minimum necessary case references.

**Procedure.** Prepare approved first-contact brief stating project identity, purpose, unknowns, requested access, contact route, privacy handling, and whether any proposal is nonbinding. Confirm who may communicate or make commitments. Log each contact attempt and response neutrally. Obtain access for survey/diligence through owner-approved process before entry; store permission scope, dates, conditions, and revocation/status. Use nonbinding term sheet only when marked draft/nonbinding and reviewed as configured. Route offers, counteroffers, valuation, and proposed terms to authorized land lead and counsel. Record open terms, owner response, expiry, conditions, and next action. No outreach, draft, meeting note, or verbal indication means control granted.

**Negotiation/status schema.** Parcel; instrument type from configured vocabulary; party/authority verified; proposed area/use/term; valuation basis/date and reviewer; permitted access/use; compensation/conditions if applicable; restoration/maintenance/access obligations; offer and response dates; status (screening/contact/access requested/access granted/negotiation/draft review/executed/declined/disputed/unknown); approval chain; execution evidence; effective/expiry dates; obligations owner; confidentiality; source/version.

**Exceptions.** Multiple interests: map each separately; counsel identifies required parties. Unknown owner: record search/action and restrict assumptions. Refusal/no response: log attempts, options and escalation; assess alternative site/route. Confidential terms: access-restrict and redact external package. Changed footprint: invalidate affected parcel/control review and revisit terms. Dispute: preserve competing claims and escalate to counsel/authorized authority; do not mark secured. Inaccessible land: plan alternative evidence/method and state limitation.

**Acceptance.** Contact and negotiation work is complete when each parcel has verified/unknown party status, interaction history, access status, proposed instrument path, unresolved terms, accountable owner, next date, and decision on proceed/alternate/hold. Site-control gate separately requires executed/verified owner-configured evidence or documented authorized waiver/at-risk decision. Only authorized signatory executes commitments.

## DEV-09 — Community consultation and commitment tracking

**Purpose.** Make outreach accessible, traceable, and connected to design decisions while protecting personal and confidential property data. Consultation requirements and notice periods come from owner-configured current authority; this procedure sets no legal minimum.

**Plan schema.** Audience/group and why affected; geography/service; known access/language/accommodation needs and source; engagement objective; method/channel; materials version and reading level; interpreter/access support; notice source/deadline; owner; dates; venue/accessibility; response channel; privacy/records notice; escalation path; planned decision linkage; risks; review/approval.

**Response schema.** Response ID; received date/channel; participant identifier only if needed and authorized; optional anonymous status; issue/topic; attributed quote or faithful summary; location/service/option affected; sensitivity; consent/use limits; acknowledgement date; assigned responder; response and evidence; design/option change link or reason no change; closure/return date. Aggregate themes separately from identifiable submissions.

**Procedure.** Identify affected groups with service owner and liaison; record excluded or hard-to-reach groups and mitigation. Prepare clear materials describing options, impacts, uncertainty, and how feedback affects decisions. Record material versions, channels, attendance/count basis, questions, complaints, and responses without implying endorsement. Assign each material concern to owner and due date. Feed verified themes into options/risk/design registers. Publish or send response summary through authorized channel, protect private information, and log commitments with owner, due date, evidence, and completion acceptance.

**Exceptions and acceptance.** Low response is not consent; document outreach effort and decision risk. Misinformation or conflicting evidence gets fact-check task, not silent deletion. Safety/privacy concerns route to designated reviewer. Language or access barrier triggers alternative channel/support. Consultation milestone completes when planned audiences/channels and configured notice obligations are evidenced, submissions dispositioned or tracked with owner/date, response summary approved, and commitments carried into delivery registers.

## DEV-10 — Establish design basis and requirements baseline

**Roles.** Design authority controls technical baseline and release; discipline leads own calculations and discipline reviews; asset owner owns performance need and accepts asset; operator/maintainer assess operability; safety/security/environmental reviewers assess assigned risks; document controller manages revision; sponsor authorizes scope/cost/schedule impacts.

**Requirements record schema.** Requirement ID; statement and rationale; source/authority and revision; type (service, owner, interface, safety, environmental, land, permit/condition, operational, cybersecurity, maintainability, test); verification method and acceptance authority; design element/interface; priority/status; owner; evidence; date/version; assumptions; linked risk/condition; change history. Requirements should be testable where possible; mark qualitative requirement and acceptance method explicitly.

**Design basis schema.** Project/option and baseline IDs; scope, boundaries, exclusions; service demand/capacity assumptions; site/survey inputs and uncertainty; environmental/land/access conditions; operating context and design life as owner-defined; interfaces and existing asset condition; owner-selected standards/codes with source and edition; applicable permit/contract commitments; materials/site constraints; reliability/resilience basis; maintainability/spares/staffing; safety/security/cyber/data requirements; design criteria and units; calculation/model versions; deviations/assumptions; unresolved data gaps; approving authority and date.

**Procedure.** Confirm selected option and current requirements before concept design. Trace every requirement to design response and later verification evidence. Record source edition/date, not just shorthand. Discipline leads identify missing surveys and validate input fitness. Asset owner/operator review maintainability, isolation/access, staffing, spares, inspection, and service constraints. Design authority approves baseline version and review plan. Design maturity labels are owner-configured; stage labels alone do not establish completeness.

**Acceptance.** Approved design basis, requirements register, interface register, assumption/data-gap log, review plan, named design authority, and traceability matrix exist. Unverified requirements have owner and planned verification point; conflicts are escalated and not silently resolved by designer.

## DEV-11 — Progress design reviews and control revisions

**Design package schema.** Package/drawing/calculation/specification ID; discipline; title; revision; status (working, review, approved, released, superseded, as-built); originator/checker/approver; dates; applicable scope; inputs and requirement links; model/software version where material; comments and dispositions; transmittal; supersedes; downstream uses; confidentiality.

**Review workflow.** Set review scope, maturity criteria, disciplines, operator/maintainer input, and response date before issue. Distribute controlled package version. Reviewers record comment ID, severity/category, exact reference, requested resolution, owner, due date. Originator responds with disposition (accept/change/reject with basis); reviewer closes or escalates disagreement. Design authority confirms required comments resolved or formally dispositioned and residual risks assigned. Release transmittal identifies exact revisions and permitted use. Keep review comments and superseded revisions retrievable.

**Change request schema.** Change ID; initiator/reason; affected requirement and package revision; proposed change; safety/service/quality/environment/land/permit/contract implications; cost and schedule range/basis; procurement/vendor effect; operations/maintenance/training/spares effect; interface and configuration effect; alternatives; urgency; reviewers; decision authority; approved/rejected/deferred status; conditions; implementation owner; verification evidence; as-built/document updates.

**Change procedure.** Freeze current baseline reference. Screen change for emergency field condition versus planned change. Assess all linked requirements, permits/land terms, procurement, construction, service continuity, cost, schedule, and operations impacts. Obtain delegated approvals before implementation, except owner-defined controlled emergency response path; record retrospective review when that path permits it. Update affected drawings, work packages, tests, risk, and asset records. A changed interface notifies downstream owners. Field redlines remain provisional until checked, approved, and incorporated into as-built set.

**Acceptance.** Gate/release states identify complete review set, closed or dispositioned comments, approved revision, outstanding deviations/risks with owners, and authorized release. Unapproved documents cannot appear as current-for-work. Change closes only when implementation and verification evidence link to new baseline and superseded version remains available.

## DEV-12 — Long-lead early-release gate

**Purpose.** Allow carefully bounded early procurement planning or release when schedule benefit warrants it, while making design, funding, interface, and cancellation exposure visible. This is a configurable owner gate, not a presumption that early release is authorized.

**Candidate record.** Equipment/package ID; vendor/market lead-time source and date; required-on-site date and schedule logic; design maturity; specification revision; unresolved performance/interface assumptions; supplier availability/alternatives; land/access/storage constraints; compatibility and standards review; cost range, escalation/cancellation exposure, and funding authority; procurement route and competition/contract review; warranty/storage/obsolescence; inspection/testing requirements; spares/maintenance/training; permit/condition dependencies; required-by decision date; release scope and exclusions.

**Gate checks.** Engineering confirms stable minimum technical envelope and states open interfaces, tolerances, owner, and closure date. Operations/maintainer reviews access, maintainability, spares, and obsolescence. Procurement and counsel review permissible package/contract mechanism and cancellation terms. Finance confirms available authorized funding and exposure basis. Project controls confirm schedule benefit and float assumptions. Asset owner/design authority approve deviations from normal maturity gate if owner policy allows. All applicable external conditions and site/storage needs are checked by assigned authority.

**Decision record.** Release/hold decision; specific limited scope and revision; excluded work; unresolved assumptions; exposure ceiling/source; cancellation or change consequences; interface freeze date; stop conditions; approvals/delegation; supplier commitment evidence; downstream design/procurement actions; review date. Pending funding or unapproved commitment authority blocks release. Early release does not authorize construction, installation, energization, or use.

**Acceptance.** Release packet includes approved scope/revision, stable envelope, interface owners and dates, cost/termination exposure, funding/authority evidence, reviewed contract path, risks and stop conditions, and traceable vendor acknowledgement. Any changed envelope returns for impact review; unauthorized commitment remains exception until dispositioned by authority.

## DEV-13 — Plan service continuity, cutover, and return to service

**Purpose.** Ensure design and delivery preserve, intentionally interrupt, or safely transfer service under an approved operating plan. Operations authority controls service transitions under local procedures.

**Continuity plan schema.** Service/asset boundary; baseline and critical dependencies; affected users/interfaces; current operating owner; proposed outage/transfer windows and basis; demand/seasonal constraints; temporary/bypass/redundant arrangements; capacity and limitations; failure modes and contingency; access/isolation responsibilities; communications audiences/channel/notice source; permits/land/vendor dependencies; monitoring and rollback triggers; restoration criteria; command and escalation contacts; decision authority; test/commissioning prerequisites; residual risk; evidence/approval version.

**Cutover work package.** Step ID/order; prerequisite and hold point; accountable role and performing crew; affected system/equipment; isolation/permit reference as locally configured; verification evidence; communications/acknowledgement; expected duration; decision to proceed; abort/rollback condition; contingency owner; actual start/end; exception/deviation; operations acceptance. Attach current controlled drawings, switching/operating instructions and method statements under authorized systems; this register is not itself an operating instruction.

**Procedure.** At concept, identify outages, interfaces, temporary service and affected parties. At design review, validate cutover feasibility with operator, maintainer, safety, and external operators. Before execution, confirm approved plan version, prerequisites, roles/competence evidence as required by owner, current asset state, permissions, notices/acknowledgements, contingency resources, rollback feasibility, and go/no-go authority. Log readiness review and decision. During cutover, record actual steps, hold points, deviations, service state and communications. If stop/rollback trigger occurs, hand control to designated operations authority and follow approved local plan. After work, verify restoration criteria, monitor for configured period, resolve defects, update as-built/configuration, and obtain operator acceptance.

**Exceptions.** Unplanned outage: invoke owner incident process and link incident case; do not improvise sequence in tracker. External operator unavailable: block affected step or use documented approved contingency. Temporary system fails: stop/rollback under authorized plan and record service impact. Changed sequence or condition: re-review affected hazards, dependencies, notices and approvals. Partial service return: record scope, limitations, monitoring owner, expected full restoration, and next update.

**Acceptance.** Cutover closes with actual work evidence, deviations dispositioned, service state confirmed by operations, temporary arrangements removed or assigned with expiry/review, defects and monitoring owned, asset/configuration records updated, and stakeholders notified as planned. Commissioning or physical completion alone is not service acceptance.

## DEV-14 — Discover and reconcile asset configuration

**Trigger and owner.** Use when intake references an asset that cannot be matched, asset records conflict, or service boundary crosses several systems. Asset information manager owns discovery; asset owner and operator validate operational identity; GIS/data custodian maintains source lineage; engineering confirms technical configuration.

**Discovery record.** Search terms/IDs; candidate asset IDs; source systems and extraction dates; spatial match method and coordinate reference; parent/child relationships; owner/operator/maintainer claims; installation/configuration dates and status; drawings and inspection records found; discrepancies; confidence; access restrictions; reviewer; unresolved question and owner. Mark each candidate as confirmed, possible, rejected, retired, or unknown. Keep the source record and query/extract reference so later reviewers can reproduce the match.

**Procedure and handoff.** Search approved asset, GIS, maintenance, incident, drawing, and operator records. Compare identifiers, location, function, connectivity, and effective dates; do not resolve conflict solely by nearest map point. Ask the claimed owner/operator to confirm service boundary and current configuration. When no reliable record exists, create provisional asset references with explicit uncertainty and field verification task. Hand the reconciled asset map and discrepancy list to baseline owner (DEV-03) and appraisal team (DEV-04). Update authoritative asset register only through its owning change process; this case stores a linked proposal and accepted evidence.

**Failure branches.** Conflicting IDs: preserve all candidates, assign reconciliation authority, and use temporary case ID. Missing drawings: commission survey/inspection with access, safety and method review. Asset is outside owner's control: route to interface owner and capture dependency. Sensitive map: restrict geometry and provide generalized version for broad reporting. Unknown configuration does not stop urgent response, but blocks design claims that rely on the unknown.

**Acceptance.** Asset owner or delegated custodian accepts identity/configuration or explicitly accepts provisional status; service boundary, lineage, confidence and outstanding verification task are linked to case. Handoff recipient acknowledges the exact map/register version.

## DEV-15 — Rank and route intake across portfolio

**Purpose.** Provide consistent triage across cases without pretending a numeric score determines investment or safety priority. Portfolio coordinator prepares a comparable view; service/asset owners validate consequences; configured authority sets priority and capacity allocation.

**Portfolio triage schema.** Case/need ID; service/asset and owner; urgency class and source; consequence of delay; affected population/service; statutory/contract/owner deadline if verified and cited; safety/environmental concern; resilience/critical dependency; strategic alignment; readiness and confidence; time sensitivity; estimated effort/cost range and basis; dependencies; duplicate/related program; capacity constraint; priority rationale; decision authority; review date/trigger; status and next action.

**Procedure.** First separate immediate response from capital prioritization. Confirm common definitions, source dates and missingness before comparing cases. Group linked needs into program candidates without merging their evidence. Show multi-criteria rationale and uncertainty; allow authorized override with reason. Record defer, study, combine, advance, or decline disposition and explicit review trigger. Maintain a visible queue for unranked or incomplete cases so missing data does not silently become low priority. Feed accepted priority and resource assumptions to case sponsor and dependency planner (DEV-06).

**Friction controls.** Use one concise evidence packet per review: need, baseline confidence, consequence of delay, options maturity, dependencies, decision requested. Prepopulate source-linked information and highlight conflicts instead of asking submitters to re-enter data. Batch similar clarifications and publish who owns each answer. Do not create duplicate submissions to fit a funding/program category; link separate classifications to same need.

**Failure branches and acceptance.** If criteria conflict, refer to authority and preserve both views; if capacity is unavailable, record queue position basis and revisit date; if urgency changes, re-triage with timestamp and notify affected owners. Acceptance requires disposition, rationale, authority, next review, and acknowledged receiving sponsor. Portfolio rank is not approval to spend or proceed.

## DEV-16 — Commission independent assurance and challenge

**Trigger.** Use at owner-configured risk, novelty, consequence, uncertainty, or decision gate. Sponsor appoints reviewer independent of authorship and approval where practicable; assurance lead agrees scope; design authority and project lead provide evidence and response.

**Assurance plan schema.** Decision/gate under review; purpose and scope; independence/conflict declaration; reviewer competence and authority; criteria/source versions; sampled evidence and rationale; assumptions and exclusions; review dates; deliverables; response owner; escalation path; limits of assurance; approval.

**Procedure.** Define questions before review (for example, whether evidence supports a decision, interfaces are closed, or operation is feasible). Give reviewer controlled versions and access to source evidence. Log finding ID, severity under configured vocabulary, reference, evidence, required response, owner and due date. Author responds with correction, accepted risk, or reason for disagreement; reviewer evaluates disposition. Decision authority accepts residual findings with explicit conditions or blocks gate per local policy. Keep assurance report separate from project self-assessment; never label review as certification unless authorized source supports it.

**Handoff and failure branches.** Late/unavailable reviewer: escalate schedule/capacity decision; do not silently waive review. Reviewer conflict: replace or document authorized mitigation. Evidence insufficient: issue bounded finding and task rather than broad untestable request. Disagreement: preserve both positions and refer to delegated authority. Acceptance requires scope, independence check, findings, dispositions, residual actions, authority decision, and evidence version archived with gate packet.

## DEV-17 — Coordinate utility conflicts and relocation interfaces

**Trigger and roles.** Use when proposed works may encounter or affect existing utility, network, drainage, access or third-party assets. Project utility coordinator maintains register; each asset owner/operator confirms records and requirements; survey/engineering defines conflict; land lead secures access; construction planner sequences resolution.

**Conflict register schema.** Conflict ID; proposed work geometry and revision; utility/asset ID and owner; record source/date/reliability; survey method/date and confidence; depth/elevation/reference where available; uncertainty/tolerance; affected design element; owner contact and response; protection/avoidance/relocation option; outage/interface requirement; permit/access/easement dependency; design and cost/schedule range; responsible party; agreement/approval status; required-by date; field verification/hold point; evidence and closeout status.

**Procedure.** Request records from identified operators and capture response or no-response; treat records as indicative until field verification specified by owner. Compare utilities against current design revision and survey basis. Convene affected operators to confirm ownership, access, protection/relocation concept, service window, cost responsibility, and approval path. Model alternatives (avoid, protect, relocate, sequence) with service continuity and land implications. Assign each conflict a disposition and design reference; unresolved high consequence conflicts become explicit gate blockers or authorized conditional releases with limits. Before work near conflict, verify current field evidence and operator's required notification/attendance; record hold-point release. After relocation/protection, capture as-found/as-built evidence and operator acceptance, then update interface and asset records.

**Failure branches and friction reduction.** Unknown owner: coordinate records search through asset information lead and do not infer ownership from markings. Inaccurate records: stop affected design/work, log verified location and rework assessment. Operator nonresponse: escalate through owner-configured interface channel and show schedule exposure. Multiple operators: maintain one coordination meeting/action log with separate technical approvals. Changed alignment: rerun conflict query against new revision and notify previous reviewers. Acceptance requires each conflict avoided, resolved, protected, or explicitly risk-accepted by authority, with evidence and downstream owner acknowledgement.

## DEV-18 — Seasonal, staged, and fallback delivery planning

**Purpose.** Plan delivery around seasonal loads, environmental/access windows, service peaks, supply uncertainty, and partial-capacity commissioning. Sponsor and planner own phasing; operations authority validates service effects; engineering confirms technical interfaces; land/community leads confirm access/commitment effects.

**Scenario register.** Scenario ID; trigger (season/date, demand, weather/access condition, vendor delay, permit/land condition); evidence/source and confidence; affected scope/phase; service demand/capacity; temporary arrangement and limits; dependencies; cost/schedule effect range; environmental/community impact; safety/operational constraints; fallback option; decision authority; activation and exit criteria; owner; review date.

**Procedure.** Develop baseline and adverse scenarios, not only preferred calendar. Identify irreversible steps and last responsible decision dates. Define phase boundaries, interfaces, test/acceptance evidence, and minimum viable service for each phase. For fallback, verify funding authority, land/access rights, compatibility, operating resources, vendor availability and rollback feasibility before claiming it is executable. Link temporary works to inspection/expiry owner and removal/restoration task. Revisit scenarios when forecast or condition crosses a configured trigger; record actual activation and lessons.

**Acceptance and failure branches.** Operations accepts interim service limitations and monitoring before phase start. If fallback is unverified, label it contingency concept and keep gate at risk. If seasonal window missed, reforecast impact and obtain decision on defer, resequence or revised method; do not compress review steps by schedule assertion. Each phase has authorized start/stop criteria, owner, dependencies and evidence, plus a documented path to final integrated service acceptance.

## DEV-19 — Release construction work package from design baseline

**Purpose.** Provide a controlled handoff from design/procurement readiness to field execution. This gate does not replace a notice to proceed, safety permit, statutory approval, or contractor method review; configured authorities remain responsible.

**Release packet schema.** Work package ID/scope and location; design baseline and exact released drawing/spec revisions; linked requirements and acceptance criteria; field constraints and utility conflicts; land/access/permit conditions and evidence; procurement and vendor submittal status; long-lead interface status; quality inspection/test points; hold/witness points and releasing role; construction sequence; service/outage/cutover links; temporary works and restoration; risk/hazard controls references; environmental/community commitments; materials/substitutions; approved deviations; cost/schedule authorization; contractor/owner roles; emergency contacts; transmittal and acknowledgement.

**Readiness review.** Discipline leads confirm constructible design and closed/dispositioned comments. Survey and field condition basis is current enough for released scope. Utility conflict dispositions and required operator coordination are in package. Land lead confirms documented access scope and restrictions. Permit/condition owners confirm applicable prerequisites and obligations. Procurement confirms approved-for-use vendor data and substitutions. Operations confirms outage, isolation, temporary service and acceptance interfaces. Quality confirms inspection/test evidence path. Project authority confirms funding, contract and release delegation.

**Decision and friction controls.** Run one cross-functional release review against a prefilled checklist with linked source evidence; assign only exceptions, not re-keyed facts. Record each blocker with owner, due date, affected work area, and resolution evidence. Release by bounded area/package where prerequisites differ; do not imply whole-project readiness from one released segment. Decision records exact revision, scope, conditions, stop-work triggers, authority, and recipient acknowledgement. Field RFI or changed condition routes to DEV-11 change control; superseded package is visibly withdrawn from active use.

**Failure branches and acceptance.** Missing access, unresolved conflict, stale survey, pending condition, unapproved substitution, or unaccepted outage plan blocks affected scope; unaffected packages can proceed only if interfaces and separation are documented. Emergency work follows owner's separate authorized path and is retrospectively linked to design/as-built records. Package is accepted for release when every required role signs or has documented disposition, current controlled set is transmitted, receiver acknowledges version, open items have bounded scope/owners, and authorization evidence is stored.

## Cross-procedure gate checklist

Before any stage transition, case manager confirms: correct case and current versions; owner/receiver acknowledgements; source-linked evidence accepted by named reviewer; decision authority/delegation recorded; open conditions, risks, data gaps and dependencies visible; waivers/at-risk items justified and approved; notifications and restricted-data access appropriate; downstream records linked; next owner and date assigned. Stage gate status must not conceal a pending or rejected review.
